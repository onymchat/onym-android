# BSN naming provider (experimental HTTP profile)

This contribution adds an opt-in adapter for the deployed [BSN provider](https://atlas.predhit.com/bsn-np/) to the Android client. The concrete wire profile is `onym:naming-implementation:bsn-stellar-http-v1`; it is not a claim that every Onym naming provider uses this encoding. The [API specification](https://atlas.predhit.com/bsn-np/protocol.md) and [Russian walkthrough](https://atlas.predhit.com/bsn-np/guide/) describe the same service used by Onym Web.

## Try it

1. Open Settings → Identities → the active identity. Find **BSN name provider**.
2. In an external Stellar wallet, set `Name` on the account whose name you want to use (an existing lowercase `name` is also supported). Add `OwnershipFull` or an unused `OwnershipFullN` data entry containing the Onym Stellar address displayed by the app. An account equal to the Onym Stellar address needs no extra binding. Sign and submit that transaction with the Stellar account's wallet.
3. Enter that account's public G-address in Android and choose **Request name**. The identity signs a short-lived issuance request inside `IdentityRepository`.
4. Review the returned name and publication notice, then **Accept and publish**. The client signs the specific record digest; the public provider can now associate this Onym signing key with the Stellar account.
5. Enable **Show BSN names in chats** separately for each viewing identity. In an open multi-person chat, sender headers and reply attributions use verified names from that provider. The label includes the namespace and a shortened Stellar account because display names are not unique. Existing one-to-one chat layout hides sender headers; this change preserves that layout.
6. **Check my published name** loads the current record; **Disavow this name** signs a withdrawal. Changing `Name` or the binding on Stellar also invalidates the previous record at the next resolution. Request and accept a new record after a change or expiration.

The Android panel currently requires the Stellar transaction to be submitted in an external wallet. It does not build or sign Stellar transactions and does not import a Stellar secret key. The deployed web client has a transaction-builder flow.

## Verification and identity boundaries

The client pins the provider's Ed25519 trust root and HTTPS origin. It verifies the signed manifest, resolution envelope, individual record, holder acceptance, record digest, scope, subject, policy, status, and expiration before displaying a name. Signatures use sorted-key UTF-8 JSON with `onym-bsn-np-v1:<kind>\n` domain separation. The subject is `onym:key:<32-byte Ed25519 signing public key hex>`, not a BLS member identifier or inbox key.

Mutations use the existing `signWithStellarKeyAs(owner, bytes)` boundary. The UI and HTTP adapter receive detached signatures, never secret key material. Viewing consent belongs to the chat's `ownerIdentityId`, is off by default, and is removed when that identity is deleted. The identity management panel is available for the active identity only.

The presentation map is derived from the existing group member profiles. Names do not replace membership, BLS identifiers, routing keys, stored aliases, invitations, or sender verification. They are annotations made after the existing chat verification path. The provider's signature attests to its BSN observation, not the real-world identity or uniqueness of the person.

## Network and privacy

Enabling display sends the open chat's participant signing public keys to the provider, which also sees the network request's IP address. Public acceptance exposes the account-to-Onym-key association. Both actions have separate UI controls and explanatory text. Simply opening identity settings makes no provider request.

Lookups run only while the chat lifecycle is STARTED, refresh after each pass plus 30 seconds, and are capped at the first 20 member profiles per chat. Signed status expires within 60 seconds. Offline, rejected, revoked, disavowed, unaccepted, or expired records fall back to ordinary aliases. Names remain only in composition memory; only viewing consent is persisted. HTTP responses are size-limited, redirects are disabled, and requests use a separate unauthenticated HTTP client with a 12-second timeout.

## Tests and current limits

`BsnNamingClientTest` consumes `app/src/test/resources/naming/bsn-v1.json`, generated by the Node provider from test-only deterministic Ed25519 seeds (issuer byte 41, holder 42, account 43). No real account or production private key is used. The fixture covers Cyrillic and emoji, canonical record digests, unaccepted and revoked status, missing acceptance and a signed acceptance for the wrong digest. Tests additionally reject stale/future envelopes, another issuer, wrong subject/policy and tampering.

Run `./gradlew :app:testDebugUnitTest --tests '*BsnNamingClientTest'` and the repository's two secret-boundary lint scripts. Full Android compilation, instrumentation and device checks are separate from the portable verifier tests. This adapter deliberately has one pinned provider; generic discovery/provider selection, batching for large groups, automatic renewal and a native Stellar transaction builder are follow-up work.
